--- CLAUDE 30698a20810c REJECT
The patch discards the active indices that belong to the computed basis values and fetches coefficient rows with those indices without any bounds check.

1. **The active indices can be wrong.** `this->basis().compute(in, tmp)` fills `tmp.actives` along with `tmp.values`, and the two are computed together. The patch then overwrites them:
   ```cpp
   this->basis().active_into(in, out.actives);
   tmp.actives = out.actives;
   ```
   The original `gsGeometry::compute` uses `out.actives = tmp.actives`, so values and indices always match. Here they come from a separate `active_into(in, ...)` call. For a composed basis, the actives should come from the composed points (the composition evaluated at `in`), not from `in` itself. If `active_into` isn't overridden the same way as `compute`, the indices will not match the rows of `tmp.eval(p)`, `tmp.deriv(p)` and `tmp.deriv2(p)`. Every value and derivative would then silently use the wrong coefficients.

2. **The coefficient lookup can read out of bounds.** `extractRows(m_coefs, tmp.active(p), coefM)` was replaced with a hand-written loop:
   ```cpp
   coefM.row(r) = m_coefs.row(tmp.active(p)(r,0));
   ```
   Eigen's `row()` only checks bounds in debug builds. Combined with the first issue, an index that is inconsistent or past the last coefficient row reads out of bounds from `m_coefs` in release builds.

3. **There is also extra work.** The actives are computed twice for every call. The original line `if (flags & NEED_ACTIVE) out.actives = tmp.actives;` was correct and cheaper.

Fix: restore `out.actives = tmp.actives;` and use `extractRows`, or at least assert that each index is below `m_coefs.rows()`. If composed bases really need different actives, fix that inside `gsComposedBasis::compute` instead.

**Scope.** The patch adds a `compute()` override to `gsComposedGeometry` and exposes `m_coefs` through a `using` declaration. Its own comment says it is copied from `gsGeometry::compute` with the `SAME_ELEMENT` fast path removed. I compared it against that logic.

**Correctness and memory safety**
- **Buffer sizes are consistent.**
  - `out.values[0]` is resized to `numCo × numPt`, and each `reshapeCol(p, 1, numCo)` view stays inside that buffer.
  - The same holds for `values[1]` (`numCo*derS × numPt` with `reshapeCol(p, derS, numCo)`) and `values[2]` (`numCo*der2S`).
  - Each product has matching dimensions. For example, `tmp.eval(p)` (1 × nActive) times `coefM` (nActive × numCo) gives 1 × numCo, which matches the destination view. The derivative products follow the same pattern.
- **`coefM` is resized on every iteration** to the active count at that point, so a varying number of active functions per point cannot cause stale or out-of-range writes.
- **`NEED_ACTIVE` is always set** by `flags = out.flags | NEED_ACTIVE`. This guarantees `tmp.active(p)` is filled before it is used to index rows.
- **Row indexing into `m_coefs` is unchecked**, as in upstream `gsGeometry`. It relies on the basis/coefficient invariant (`m_coefs.rows() == basis().size()`) that the class hierarchy already enforces. This adds no new trust boundary, and no external input reaches the index.
- **`noalias()` is valid** because each destination is a view into `out.values` and does not overlap `tmp` or `coefM`.

**Deviations from upstream, all non-blocking**
1. `tmp.actives = out.actives;` overwrites the actives already produced by `basis().compute(in, tmp)` with the result of `basis().active_into(in, ...)` on the same basis and points. The two should be identical, so this is redundant work rather than a defect. It does mean the evaluated values and the actives come from two separate calls. A brief comment or an assertion that the row counts match would make that invariant explicit.
2. Dropping the `SAME_ELEMENT` path is documented and safe. It only gives up an optimization, which matters for a composed basis where points can map to different elements after composition.
3. The `using Base::m_coefs;` declaration is a minimal visibility change limited to the class's own `protected` section.

**Out of scope, pre-existing.** The move assignment calls `Base::operator=(other)` on an rvalue, which performs a copy rather than a move. This is a performance point only, and the patch does not touch it.

**Security assessment.** The patch introduces no new input parsing, allocation driven by untrusted sizes, raw pointer arithmetic, lifetime hazards, or ownership changes. Any memory-safety exposure reduces to invariants that the existing `gsGeometry` implementation already depends on. Nothing here warrants rejection. Optionally, adding a debug-time `GISMO_ASSERT` that `tmp.active(p).rows()` matches the column count of `tmp.eval(p)` would make the implicit invariant explicit.
--- TEST-FOCUSED 939526b1bf45 REJECT
**Main silent path: the `SAME_ELEMENT` flag is still forwarded to the basis.**

The override exists to drop `gsGeometry::compute`'s `SAME_ELEMENT` shortcut, which is wrong for a composed geometry because the composition can map points into different elements. But the code does `flags = out.flags | NEED_ACTIVE` and passes those flags straight to `this->basis().compute(in, tmp)`. If a caller sets `SAME_ELEMENT`, the basis may:

- compute actives only from `in.col(0)`, and
- shape `tmp.values` around that single element's active set.

The patch then overwrites `tmp.actives` with per-point actives from `active_into(in, out.actives)`. This pairs basis values computed under one active set with coefficient indices taken from another. The output keeps the right shape and finite, plausible numbers, so nothing throws and no size check fires. The geometry values and derivatives are just wrong. The error only appears when the evaluation points straddle element boundaries after composition, which depends on the composition map and the quadrature layout.

The overwrite of `tmp.actives` also hides any mismatch between what `basis().compute` produced and what `active_into` returns, because the internally computed actives are thrown away without comparison. The fix is to strip the flag explicitly, e.g. `const unsigned flags = (out.flags | NEED_ACTIVE) & ~SAME_ELEMENT;`, so the basis is never asked for the single-element shortcut.

**Secondary silent paths:**

1. **Unchecked indexing.** `coefM.row(r) = m_coefs.row(tmp.active(p)(r,0))` has no bounds check. If the basis and `m_coefs` disagree on size, a debug build asserts but a release build reads out of bounds and returns garbage. Whether this fails loudly depends on the build configuration.
2. **Stale output data.** `out.values.resize(out.maxDeriv()+1)` keeps earlier entries, but only resizes and fills `values[0]`, `values[1]` and `values[2]` when their own flag is set. If `out` is reused, say a `NEED_DERIV`-only call after a `NEED_VALUE` call, `out.values[0]` still holds results for the previous points. Those values look valid. Likewise, if a flag raises `maxDeriv()` to 2 (e.g. a Hessian or Laplacian request) without `NEED_DERIV2`, `values[2]` is left empty or stale instead of failing.
3. **Constant active count assumed.** `tmp.eval(p)` and `tmp.deriv(p)` assume the same number of active functions at every point, but `coefM` is sized from `tmp.active(p).rows()` for each point separately. If the composed basis yields different active counts at different points, the reshape layout of `tmp.values` no longer matches `coefM`, giving wrong products with no error.

Path 1 alone could pass as an inherited pattern from `gsGeometry`. But the `SAME_ELEMENT` forwarding defeats the stated purpose of this override and produces plausible wrong values that depend on the data, which is enough to reject.
