--- CLAUDE 30698a20810c REJECT
**Main defect: about 4× more objective evaluations in the default gradient.**

- **Before:** forward difference, `(e1 - e0) / h`. It evaluates `e0` once outside the loop, then once per coordinate, for **n + 1** calls to `evalObj` in total.
- **After:** five-point central stencil. Each coordinate needs `e1`, `e2`, `e3` and `e4`, for **4n** calls in total.

`evalObj` is usually the expensive part, such as a PDE solve or an assembly plus solve in G+Smo shape optimization. So this roughly quadruples the cost of every gradient for any subclass that does not override `gradObj_into`. That cost repeats on every optimizer iteration. For large `n`, it can turn a workable run into an impractical one.

**The math is correct.** `(8(f(x+h) − f(x−h)) − f(x+2h) + f(x−2h)) / (12h)` with `12h = 0.00012` is the standard O(h⁴) stencil, and the ordering of `e1` through `e4` is right. Even so, the change has these problems:

- **It silently changes cost and accuracy for all callers.** The more accurate stencil should be an opt-in choice, such as a flag, a template or strategy parameter, or a separate method, rather than the new default.
- **The accuracy gain is limited at this step size.** With a fixed `h = 1e-5` in double precision, rounding error grows as ε/h, so the higher-order stencil does not improve accuracy by as much as its 4× price suggests.
- **It brings back code that had been deliberately commented out,** apparently because of this same cost trade-off. The patch gives no benchmark or reason for reversing that.
- **The bounds-check TODO is still open and now matters more.** The stencil now evaluates at `u ± 2h`, which can step outside `m_desLowerBounds` and `m_desUpperBounds`.

**Recommendation:** keep the cheap forward difference as the default, or at most use a 2n-call central difference. Offer the five-point stencil as an optional mode.

--- ADVOCATE 32e59155d0a3 REJECT
**The patch introduces a clear performance regression on a default code path.**

**Cost comparison.** The old default was a forward difference:
- One baseline evaluation `e0`, hoisted out of the loop.
- One evaluation per design variable.
- Total: **n + 1** calls to `evalObj` per gradient.

The new code is a 4-point central difference:
- Four evaluations per design variable (`e1`, `e3`, `e2`, `e4`).
- Total: **4n** calls to `evalObj` per gradient.

For any non-trivial n, each gradient now costs about 4× as much. This matters because:
- `gradObj_into` is the fallback for every subclass that doesn't override it, so the slowdown affects all such users without them opting in.
- `evalObj` in this setting (shape or parameter optimization in G+Smo) often means assembling and solving a PDE system, so each call is expensive.
- Optimizers call the gradient every iteration, often many times.

**Correctness is fine.** The formula `(8·(f(x+h) − f(x−h)) − (f(x+2h) − f(x−2h))) / (12h)` with h = 1e-5 is the standard 4th-order central stencil. The code computes `8*(e1-e2) + e4 - e3` over `0.00012`, which matches. Resetting `tmp[i] = u[i]` restores the copy correctly. So this is a deliberate accuracy-for-cost trade, not a math bug.

**Why reject anyway.** Accuracy alone doesn't justify the cost here:
- The comment says "overriding it should provide exact gradient," so callers who need accuracy are expected to override.
- Truncation error is not the main problem with a 1e-5 step. Error at that step size is usually dominated by cancellation and by noise in `evalObj` (e.g. iterative-solver tolerance). A higher-order stencil doesn't fix either.
- The patch silently makes the default about 4× more expensive, with no option to choose between schemes.

**Suggested fix.** Keep the forward difference (with the hoisted `e0`) as the default. If higher accuracy is wanted, add the central/4-point scheme as an opt-in, for example via an option or a separate method.
