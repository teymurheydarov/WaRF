=== ONE decision REJECT
[REJECT] The new `gsRationalBasis<SrcT>::derivSingle_into` declares its source-basis buffers with the wrong scalar type:

```cpp
gsMatrix<> N, dN;
m_src->evalSingle_into (i, u,  N);
m_src->derivSingle_into(i, u, dN);
```

- `gsMatrix<>` defaults to `real_t`, not the basis scalar `T`.
- `evalSingle_into` and `derivSingle_into` take `gsMatrix<T>&`. A non-const reference cannot bind to a matrix of a different scalar type.
- So if `T` is anything other than `real_t` (e.g. `float`, `long double`, or an AD or multiprecision type), this does not compile.
- If `T` happens to equal `real_t`, the result mixes `T` and `real_t` in `W(0,j)*dN.col(j) - N(0,j)*dW.col(j)`. That only works by coincidence.
- Every other buffer in the function (`W`, `dW`, `result`) correctly uses `gsMatrix<T>`, so this is an inconsistency, not a deliberate choice.

The math itself is right: R_i' = w_i (N_i' W − N_i W') / W². The shapes also fit: `W` is 1×n, and `dW` and `dN` are Dim×n. But the buffers must be `gsMatrix<T> N, dN;`.

Minor issues, not blocking:
- `math::pow(W(0,j),2)` is better written as `W(0,j)*W(0,j)`.
- The function evaluates the full weight function on every call. That is expensive per basis function, but not a defect.

=== FIVE decision APPROVE
--- SKEPTIC [APPROVE]
The new `derivSingle_into` is mathematically correct, and I could not construct an input, state or call sequence that gives a wrong result.

**Formula.** The derivative of a rational basis function R_i = w_i N_i / W is R_i' = w_i (N_i' W − N_i W') / W². The loop computes `m_weights.at(i) * (W(0,j)*dN.col(j) - N(0,j)*dW.col(j)) / W(0,j)^2`, which matches term for term:
- The sign is right.
- The weight index is right (`at(i)`, the queried function, not an active-set index).
- The denominator is squared.

**Shapes.**
- `evalFunc_into(u, m_weights, W)` with a single-column coefficient matrix gives W as 1 × n.
- `derivFunc_into` gives dW as Dim × n.
- `evalSingle_into` gives N as 1 × n.
- `derivSingle_into` gives dN as Dim × n.
- `result.resize(Dim, u.cols())` matches the per-column assignment.
- All indices `(0,j)` and `.col(j)` are in bounds.

**Weight function.** W and W' are computed globally from all weights, not just the local support. The result is still correct, because inactive basis functions are zero at the evaluation points. It does more work than needed but is not wrong.

**Division by zero.** W = 0 is only possible with invalid weights. The existing `deriv_into` and `deriv2_into` make the same assumption, so this introduces no new hazard.

**Rest of the patch.** The other changes are cosmetic and do not change behaviour:
- the new declaration in the header;
- a commented-out `deriv2Single_into` declaration;
- removal of one blank line.

The surrounding `deriv_into` and `deriv2_into` code is unchanged context, and I checked its formulas as well (N'W − N W' scaled by w/W²; the second-derivative and mixed-derivative terms).

**Minor nit (not a demonstrated defect).** `gsMatrix<> N, dN;` uses the default scalar type rather than `gsMatrix<T>`. When T is `real_t`, which is the normal instantiation, this is the same type and behaves identically. With a different scalar type it would fail to compile rather than silently give wrong results. Changing it to `gsMatrix<T>` for consistency is recommended, but it does not cause incorrect runtime behaviour.
--- ADVOCATE [APPROVE]
**Formula check.** The new `derivSingle_into` correctly implements the quotient rule for a rational basis function, R_i = w_i·N_i / W:

- `W` comes from `m_src->evalFunc_into(u, m_weights, W)`, giving W = Σ w_k N_k as a 1×n matrix.
- `dW` comes from `m_src->derivFunc_into(u, m_weights, dW)`, giving W′ as a Dim×n matrix.
- `N` and `dN` are the source basis value N_i (1×n) and its gradient N_i′ (Dim×n).
- For each point j, the result is `w_i * (W·dN − N·dW) / W²`, which matches the comment R_i′ = w_i(N_i′W − N_iW′)/W².
- `result.resize(Dim, u.cols())` matches the single-function derivative layout of Dim rows per evaluation point.

Using `m_weights.at(i)` with the global index `i` is correct, because `evalSingle_into` and `derivSingle_into` are also called with the global index. This produces the same values as the corresponding Dim-row block of the existing `deriv_into`, just evaluated for one function.

**Other changes.** The remaining edits are harmless:
- the new declaration in the header,
- a commented-out `deriv2Single_into` stub,
- removal of one blank line.

None of them changes behavior of `deriv_into` or `deriv2_into`.

**Minor nit (not blocking).** `gsMatrix<> N, dN;` uses the default scalar type (`real_t`) instead of `T`. When T is real_t, which is how the library is normally instantiated, this behaves identically. With a different scalar type it would fail to compile rather than silently give wrong results. Changing it to `gsMatrix<T>` would make it consistent with the surrounding template code. Similarly, `W(0,j)*W(0,j)` could replace `math::pow(W(0,j),2)`, but that is only stylistic.

I found no clear functional defect.
--- AUDITOR [REJECT]
**Main defect: wrong scalar type for `N` and `dN`**

- `gsRationalBasis<SrcT>` is generic over the scalar type `T` (`SrcT::Scalar_t`), and every other buffer in the new function uses `gsMatrix<T>`.
- `N` and `dN` are instead declared as `gsMatrix<>`, which defaults to `real_t`.
- They are passed to `m_src->evalSingle_into(i, u, N)` and `m_src->derivSingle_into(i, u, dN)`, which take a `gsMatrix<T>&`.
- For any build where `T` is not `real_t` (float, long double, mpreal, or a different `real_t` configuration), this will not compile. A non-const reference cannot bind to a matrix of a different scalar type.
- Even if it did compile, the result line would mix `T` and `real_t` in one Eigen expression, which Eigen rejects without explicit casts.
- The fix is simple: use `gsMatrix<T> N, dN;`. As written, though, the patch breaks the class's genericity.

**What is correct**

- The math matches the stated formula, R_i' = w_i (N_i' W − N_i W') / W².
- `W` comes from `evalFunc_into` with the weights as coefficients, giving a 1×n matrix.
- `dW` comes from `derivFunc_into`, giving a Dim×n matrix for a single coefficient column.
- `N` (1×n) and `dN` (Dim×n) come from the single-function evaluators.
- `result` is sized Dim×n, which matches the layout `derivSingle_into` uses elsewhere.

**Minor issues (not blocking on their own)**

- `math::pow(W(0,j),2)` is less efficient and less exact than `W(0,j)*W(0,j)`, which the existing `deriv_into` and `deriv2_into` use.
- There is no `GISMO_ASSERT` that `i` is within `[0, size())` before `m_weights.at(i)`.
- The function evaluates the whole weight function (all basis functions) to get one basis derivative. This is acceptable but inefficient.
- The commented-out `deriv2Single_into` declaration and the removed blank line are harmless noise.

The patch should be resubmitted with `gsMatrix<T>` for `N` and `dN`.
--- TEST-FOCUSED [REJECT]
**Defect: hardcoded scalar type in the new `derivSingle_into`**

```cpp
gsMatrix<> N, dN;
m_src->evalSingle_into (i, u,  N);
m_src->derivSingle_into(i, u, dN);
```

Every other matrix in this class template uses `gsMatrix<T>`, including `W` and `dW` two lines above. `gsMatrix<>` is `gsMatrix<real_t>`, so the code only works when `T == real_t`.

- `evalSingle_into` and `derivSingle_into` take `gsMatrix<T>&`. For any other instantiation (`float`, `long double`, `mpreal`, or a non-default `real_t` build), the non-const reference cannot bind to a `gsMatrix<real_t>`, so the code fails to compile.
- The breakage stays hidden until someone instantiates the template with a different scalar type. A test suite built with the default `real_t` will never catch it.
- The fix is `gsMatrix<T> N, dN;`.

Being loud at compile time does not excuse it. It is an outright defect in a generic template.

**Secondary: a silent numeric failure path**

The result is divided by `math::pow(W(0,j),2)` with no guard. If the weight function evaluates to zero at a point (zero or cancelling weights, or a point where all active weighted basis values vanish), the function returns `inf`/`NaN` columns without raising anything. This mirrors the existing `deriv_into`, so it is not new. Still, the new path adds no assertion and inherits the silent failure.

**Things I checked that are correct**

- **Formula:** `R_i' = w_i (N_i' W − N_i W') / W²` is correct.
- **Shapes:** `W` is 1×n from `evalFunc_into`, `dW` is Dim×n from `derivFunc_into` with scalar weights, `N` is 1×n and `dN` is Dim×n. All of these agree with `result.resize(Dim, u.cols())`.
- **Override:** it still works without the `virtual` keyword, because the base declaration is virtual.
--- BOUNDARY [APPROVE]
The new `derivSingle_into` is correct, and no boundary I traced produces a wrong result. One type issue is noted below, but it is not a boundary defect.

**Formula check.** The function computes R_i' = w_i (N_i' W − N_i W') / W². It matches the existing `deriv_into`, which builds `W·N'`, subtracts `N·dW`, then scales by `w/W²`. The shapes line up:
- `W` from `evalFunc_into(u, m_weights)` is 1×n.
- `dW` from `derivFunc_into` is Dim×n, since the weights are scalar.
- `N` is 1×n and `dN` is Dim×n.
- `result` is resized to Dim×n, and each column is a Dim-vector expression.

**Boundaries traced:**
- **`u.cols() == 0`:** every source call returns an empty matrix, `result` becomes Dim×0 and the loop is skipped. This is correct (a).
- **`u.cols() == 1`:** the loop runs once over j = 0 with no off-by-one; it uses `j < u.cols()`. Correct (a).
- **`i` outside [0, size)**: `m_weights.at(i)` and the source's `evalSingle_into(i, …)` would misbehave. The `*Single_into(i, …)` API in this codebase requires a valid index, and the existing `evalSingle_into` has the same precondition. Unreachable under the contract (b).
- **`W == 0`, causing division by zero:** rational bases require positive weights, and the source basis is a partition of unity, so W > 0 on the domain. `deriv_into` and `deriv2_into` already divide by `W*W` with the same assumption. Unreachable under the contract (b).
- **`u` outside the support of basis i:** `N` and `dN` are 0, so `result` is 0, which is the correct derivative of R_i there. Correct (a).
- **Negative or zero `w_i`:** this violates the rational-basis contract, and the result would still match the formula. (b)

**Other hunks.** The rest of the diff is a header declaration, a commented-out `deriv2Single_into` stub, and removal of one blank line. None of these change behavior.

**Note, not a boundary defect.** `gsMatrix<> N, dN` uses the default scalar type (`real_t`) instead of `T`. If `T != real_t`, the calls to `evalSingle_into` and `derivSingle_into` would fail to compile; they would not compute a wrong value. It is worth changing to `gsMatrix<T>` for genericity, but it does not meet the bar for rejection.
