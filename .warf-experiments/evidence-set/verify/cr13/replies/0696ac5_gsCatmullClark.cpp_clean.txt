=== ONE decision REJECT
[REJECT] The defect I can point to is in the sharp-vertex branch (`2 == sd`), which this refactor copies over unchanged:

```cpp
auto h1 = mesh.halfedge(v);
while (!sharp[h1] || mesh.touches_boundary(h1))   // loop 1
    h1 = mesh.cw_rotated_halfedge(h1);
Halfedge h2 = h1;
h1 = mesh.ccw_rotated_halfedge(mesh.halfedge(v));
while (!sharp[h1] || mesh.is_boundary(h1))        // loop 2
    h1 = mesh.ccw_rotated_halfedge(h1);
```

- **The two searches use different exclusion tests.** Loop 1 skips any halfedge whose edge lies on the boundary (`touches_boundary`). Loop 2 skips only halfedges that themselves have no face (`is_boundary`).
- **It can hang.** If both sharp edges at `v` are boundary edges, which is the usual case when the boundary is flagged sharp, loop 1 rejects every halfedge around `v`. The `while` then never ends.
- **It can pick the wrong neighbour.** If only one sharp edge is on the boundary, the loops apply different rules. They can select the same neighbour twice, or mix rules. The crease result `(2v + m1 + m2)/4` is then wrong.
- **Likely fix:** use the same test in both loops, probably `is_boundary`. Also make sure the second search can't land on `h2` again.

Moving this logic into a new public static `apply(gsSurfMesh&)` exposes it to more callers. That makes this the right time to fix it rather than carry it forward.

Secondary concern:
- **Possible build break.** The patch deletes the file-level typedefs (`Point`, `Halfedge`, etc.), but the body still uses unqualified `Point tmp;` and `Halfedge h2`. That only compiles if `gsCatmullClark` or its base class declares those names. The header isn't in the diff, so I can't confirm it. Either keep the typedefs or write `gsSurfMesh::Point` / `gsSurfMesh::Halfedge`.

I checked the rest of the arithmetic and it is unchanged and correct:
- edge midpoints `/2`
- face points as the average of the 4 corner vertices
- interior edge points `/4`
- boundary vertex rule `(2v+m1+m2)/4`, which equals `(6v+a+b)/8`
- interior vertex rule `(n(n−3)v + 4ΣE − ΣF)/n²`

--- TEST-FOCUSED [REJECT]
The refactor itself is faithful. Moving from `m_mesh->` to `mesh.` in a static `apply` changes no logic. I compared every loop, and the edge-point, face-point, quad-split, crease, boundary and interior rules match the original. But the code it carries has paths whose failure would be silent, and `apply(gsSurfMesh&)` now exposes them through a new entry point.

1. **Non-quad faces give wrong face points with no error.** After edge points are inserted, the face-point loop steps through the face vertices two at a time and always divides by 4 (`tmp /= 4`). This assumes every face started as a quad.
   - A triangle gives 3 summed points divided by 4.
   - A pentagon gives 5 summed points divided by 4.
   - In both cases the result is a plausible point shifted toward or away from the origin.
   - `quad_split` then runs on the wrong vertex count. Nothing checks the face valence, and no assertion or return value tells the caller. The interior rule `tmp /= 4; // =valence(v)` makes the same assumption.

2. **Index ranges assume no deleted vertices.** The code sets `env = n_vertices()` and `fnv = n_vertices()`, then rebuilds handles with `Vertex(fnv + i)` and loops `for (i = env; i < fnv; ++i)`.
   - This assumes new vertices take indices `[n_vertices(), ...)` in order.
   - In this surface-mesh design, `n_vertices()` usually excludes deleted vertices that have not been garbage-collected yet, while `add_vertex` adds at the end of the storage.
   - On a mesh with pending deletions, the loops would treat original vertices as edge points and the wrong vertices as face centers. The result is a moved or wrongly connected mesh, not an exception.
   - The static `apply` accepts any caller's mesh without calling `garbage_collection()` or asserting there are no deletions.

3. **The crease search can hang depending on the input.** In the `sd == 2` branch, `while (!sharp[h1] || mesh.touches_boundary(h1))` has no exit if both sharp halfedges touch the boundary. The two searches also use different tests (`touches_boundary` and `is_boundary`), so they can disagree about which sharp neighbors count. Whether this hangs depends on how sharp flags spread through `insert_vertex`. A test cannot control that, and the result is a hang, not a clear failure.

4. **The only new guard disappears in release builds.** `GISMO_ASSERT(nullptr != m_mesh)` is not checked in release builds. A null mesh then becomes undefined behavior instead of a clear error.

Each of these is a path whose failure is a plausible-looking wrong mesh or a hang, not something a caller can assert on.
--- BOUNDARY [APPROVE]
This patch is a pure refactor. It replaces the `m_mesh->` member body of `subdivide()` with a static `apply(gsSurfMesh&)`, and `subdivide_impl()` forwards to it after asserting `m_mesh != nullptr`. I compared old and new line by line: every expression, loop bound, condition and constant is the same, so the patch introduces no new boundary behaviour.

**New boundary added by the patch**
- **Null mesh:** `subdivide_impl()` asserts `nullptr != m_mesh` before dereferencing. This is handled (a). In release builds where `GISMO_ASSERT` compiles out, the old code dereferenced `m_mesh` unchecked anyway, so nothing gets worse.

**Boundaries inherited unchanged from the original**
- **Empty mesh** (0 vertices, edges or faces): `reserve(0,0,0)` is fine, every range loop is empty, and `env == fnv == 0`, so both OpenMP loops run zero times. Handled (a).
- **Edges with both halfedges on the boundary** (isolated edges): these are skipped during edge-point insertion, as before. Handled (a).
- **Face-point averaging:** stepping by `++vc, ++vc` and dividing by 4 assumes quads, which after edge insertion have 8 vertices. Non-quad input is outside the Catmull-Clark caller contract in this implementation, and the behaviour is unchanged (b).
- **Edge-point valence:** dividing by a hard-coded 4 is correct because each interior edge point has exactly 2 original-vertex and 2 face-point neighbours after `quad_split`. Handled (a).
- **Low-valence original vertices:** the `n <= 2` early `continue` guards the `n*(n-3)` and `/(n*n)` terms, so a valence of 0 (isolated vertex) cannot cause division by zero. Handled (a).
- **Sharp vertex with `sd == 2`:** the first search uses `touches_boundary` and the second uses `is_boundary`. This asymmetry exists verbatim in the original. Both `while` loops could spin forever if no qualifying halfedge exists, but `sd == 2` guarantees two sharp halfedges. Outside the contract (b) and not introduced here.
- **Boundary vertex rotation:** the `while (!touches_boundary(hh))` loop terminates because `is_boundary(v)` was just checked. Handled (a).
- **Mixed-signedness loop index:** `int i` against `index_t env/fnv` is the same as before. It would only matter for meshes above `INT_MAX` vertices, which is impractical and unchanged (b).

**Typedefs**
- The removed file-scope typedefs (`Point`, `Halfedge`) are still used unqualified. This is a compile concern rather than a logic boundary. Because `apply` is a member, class-scope typedefs from `gsSubdivScheme` or the header would resolve them, and the diff gives no evidence of a wrong runtime result.

No boundary falls in category (c), meaning genuinely mishandled with a concrete input producing a wrong result.
